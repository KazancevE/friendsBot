# Сроки жизни бонусов и порядок списания (дизайн)

Дата: 2026-08-28  
Статус: реализовано  
Продукт: Telegram-бот кальянной «Друзья»

## Цель

Дать админу настройку сроков жизни бонусов и срока забора призов-купонов. При списании на кассе сначала уходят подарочные/выигранные бонусы, затем чековые — от старых к новым. Истёкшие бонусы и купоны автоматически сгорают.

## Решения из обсуждения

| Тема | Решение |
|---|---|
| «Обычные» бонусы | Только начисления с чека (`check`) |
| «Подарочные/выигранные» | `registration`, `birthday`, `manual` (положительные), `weekly_prize` |
| Срок подарочных/призовых | Одна глобальная настройка на все источники категории `gift` |
| Призовые бонусы (`weekly_prize`) | Берут TTL из глобальной настройки подарочных, не из розыгрыша |
| Срок забора купона | С момента выдачи (закрытие недельной игры) |
| Срок купона в розыгрыше | Одно число дней на всю таблицу «Призы недели» |
| Порядок списания | 1) все `gift`-лоты (FIFO), 2) `check`-лоты (старые → новые) |
| Миграция | Разделить существующий баланс по истории проводок, где возможно |
| Предупреждения о сгорании | За **7**, **3** и **1** день до `expiresAt` (фиксированные интервалы) |
| Порог уведомлений | Админ задаёт минимальную сумму бонусов; дефолт **300** |

## Дефолты

| Настройка | Ключ | Дефолт |
|---|---|---|
| Срок чековых бонусов (дни) | `checkBonusTtlDays` | 30 |
| Срок подарочных/призовых (дни) | `giftBonusTtlDays` | 15 |
| Срок забора купона — дефолт для формы | `couponClaimDaysDefault` | 10 |
| Срок забора купонов текущего розыгрыша | `couponClaimDays` | 10 (копируется из дефолта при первом запуске) |
| Мин. сумма для уведомлений о бонусах | `expireNotifyMinBonuses` | 300 |

Единица измерения — **календарные дни**.

Интервалы предупреждений (**7 / 3 / 1** день) не настраиваются — только порог суммы. `expiresAt` = `createdAt` (МСК) + N дней, конец дня 23:59:59 МСК или начало следующего дня — зафиксировать в реализации одинаково для всех типов (рекомендация: `createdAt + N * 24h` в UTC с расчётом от момента начисления, как у визита).

## Архитектура: лоты бонусов

Flat `User.balance` недостаточен для TTL и порядка списания. Вводится сущность **BonusLot**.

### Модель `BonusLot`

```
id          uuid
userId      → User
ledgerId    → Ledger (nullable, связь с проводкой начисления)
category    gift | check
initial     int   — сумма при создании
remaining   int   — остаток (≥ 0)
expiresAt   datetime
createdAt   datetime
warned7d    boolean  @default(false)
warned3d    boolean  @default(false)
warned1d    boolean  @default(false)
```

- `User.balance` остаётся **денormalized суммой** `remaining` по лотам с `expiresAt > now` (или пересчитывается при каждой операции). UI и проверка «достаточно бонусов» используют только неистёкшие лоты.
- Списание создаёт записи **LotAllocation** (лот → сколько списано) для аудита; опционально в v1 достаточно одной проводки `redeem` + обновление лотов.

### Новый тип проводки

- `LedgerType.expire` — автоматическое сгорание; `amount` отрицательный, равен сумме сгоревших лотов пользователя за прогон.

### Купоны

Расширение `Coupon`:

```
expiresAt   DateTime
status      active | redeemed | expired
```

При создании купона на закрытии недели: `expiresAt = closedAt + couponClaimDays` из текущих настроек.

Погашение: отклонять, если `now >= expiresAt` или `status === expired`.

## Категории лотов

| Ledger type | category | TTL |
|---|---|---|
| `check` | `check` | `checkBonusTtlDays` |
| `registration` | `gift` | `giftBonusTtlDays` |
| `birthday` | `gift` | `giftBonusTtlDays` |
| `manual` (amount > 0) | `gift` | `giftBonusTtlDays` |
| `manual` (amount < 0) | — | списание по порядку лотов, без нового лота |
| `weekly_prize` | `gift` | `giftBonusTtlDays` |

Отрицательная ручная правка: уменьшает `remaining` по тому же порядку, что и кассовое списание (gift FIFO → check FIFO). Новый лот не создаётся.

## Порядок списания

Функция `allocateBonusSpend(userId, amount)`:

1. Выбрать лоты `category = gift`, `remaining > 0`, `expiresAt > now`, сортировка `createdAt ASC`.
2. Если не хватило — лоты `category = check`, те же фильтры, `createdAt ASC`.
3. Если сумма лотов < amount → `insufficient`.

Применяется в `redeemBonuses` и при отрицательном `manualAdjust`.

## Начисление

Каждое положительное начисление:

1. Создать `Ledger` (как сейчас).
2. Создать `BonusLot` с `remaining = amount`, `expiresAt` по категории.
3. Увеличить `User.balance`.

## Уведомления о бонусах

Ежедневный джоб (02:00 МСК, вместе со сгоранием). Отправка только если у пользователя есть `telegramId` и нет `broadcastOptOut`.

**Порог:** сумма бонусов в событии ≥ `expireNotifyMinBonuses` (настраивает админ, дефолт 300). Строго «≥», не «>».

### Предупреждения (до сгорания)

Для лотов с `remaining > 0` проверять календарную дату `expiresAt` в часовом поясе Москвы:

| Когда | Условие | Флаг на лоте |
|---|---|---|
| За 7 дней | `expiresAt` = сегодня + 7 дней | `warned7d` |
| За 3 дня | `expiresAt` = сегодня + 3 дня | `warned3d` |
| За 1 день | `expiresAt` = сегодня + 1 день | `warned1d` |

По каждому пользователю и интервалу — **одно сообщение** с суммой `remaining` всех подходящих лотов (не по одному на лот).

Примеры текста:

- «Через 7 дней сгорят 450 бонусов. Актуальный баланс: 1200.»
- «Через 3 дня сгорят 320 бонусов…»
- «Завтра сгорят 500 бонусов…»

После отправки выставить соответствующий флаг на каждом учтённом лоте (`warned7d` / `warned3d` / `warned1d`), чтобы не дублировать.

Если сумма по интервалу < порога — флаги **не** выставлять (повторная проверка на следующий день, если лот ещё попадает в окно, маловероятна; при смене порога админом лот может попасть в уведомление позже).

### Сгорание (после истечения)

Для лотов `remaining > 0 AND expiresAt <= now`:

1. Суммировать `remaining`.
2. Обнулить `remaining`.
3. Уменьшить `User.balance`.
4. Записать `Ledger` type `expire`.
5. Если сумма ≥ `expireNotifyMinBonuses` — «Сгорело N бонусов. Актуальный баланс: M».

**Идempotency:** лоты с `remaining = 0` пропускаются; флаги предупреждений не сбрасываются при частичном списании лота до сгорания.

## Сгорание купонов

В том же джобе (или при попытке погашения):

- `Coupon` где `status = active AND expiresAt <= now` → `status = expired`.
- Уведомление гостю о купоне — **не требуется** в v1 (можно добавить позже).

## Админ UI (бот)

В меню «Настройки» добавить кнопки:

| Кнопка | Conversation | Валидация |
|---|---|---|
| Срок чековых | `setCheckBonusTtl` | int ≥ 1 |
| Срок подарочных | `setGiftBonusTtl` | int ≥ 1 |
| Срок купона (дефолт) | `setCouponClaimDefault` | int ≥ 1 |
| Порог уведомлений | `setExpireNotifyMin` | int ≥ 0 |

Экран настроек показывает текущие значения, включая порог уведомлений и напоминание «предупреждения: за 7, 3 и 1 день».

**«Призы недели»** (`setWeeklyPrizes`): после ввода N победителей и таблицы мест — один вопрос: «Срок забора купонов (дней, сейчас X)». Сохраняется в `couponClaimDays`. Дефолт при первом открытии — `couponClaimDaysDefault`.

Изменение TTL в настройках **не пересчитывает** уже созданные лоты и купоны — только новые начисления.

## Гостевой UI

- **Баланс:** сумма неистёкших лотов (совпадает с `User.balance` при консистентности).
- **История:** у положительных проводок показывать «действуют до ДД.ММ.ГГГГ», если есть связанный лот.
- **Купоны:** «Забрать до ДД.ММ.ГГГГ»; истёкшие не показывать в активных или помечать «просрочен».

## Касса (бот + Mini App)

- Списание и ручной минус — через `allocateBonusSpend`.
- Карточка гостя: доступный баланс.
- Погашение купона: проверка `expiresAt`.

## Миграция существующих данных

Скрипт миграции (Prisma migrate + data migration):

1. Добавить таблицы `BonusLot`, поля `Coupon.expiresAt`, enum `expired`, `LedgerType.expire`.
2. Для каждого `User` с `balance > 0`:
   - Загрузить кредитовые проводки (`amount > 0`), типы `check`, `registration`, `birthday`, `manual`, `weekly_prize`, сортировка `createdAt ASC`.
   - Загрузить дебетовые (`redeem`, отрицательные `manual`) — для восстановления остатков по FIFO внутри категорий **упрощённо**: симулировать списание в хронологическом порядке (gift-first, then check-old-first) и получить `remaining` на каждую кредитную проводку.
   - Для каждой проводки с ненулевым остатком создать `BonusLot`:
     - category по таблице выше;
     - `expiresAt = createdAt + TTL` (текущие настройки или дефолты);
     - если `expiresAt <= now` — лот с `remaining = 0` или сразу провести `expire` (единоразово при миграции).
   - Если после разбора истории остаток ≠ `User.balance` — создать один `gift`-лот «legacy» на разницу с `expiresAt = now + giftBonusTtlDays` и записать в comment миграции.
3. Активные купоны без `expiresAt`: `expiresAt = now + couponClaimDays` (или `createdAt` недели + days, если есть `weekId` и `closedAt`).

После миграции включить создание лотов во всех путях начисления.

## Ошибки

| Код | Когда |
|---|---|
| `insufficient` | Недостаточно неистёкших бонусов |
| `coupon_expired` | Купон просрочен |
| `bad_amount` | TTL < 1 при настройке |

## Тесты

- `allocateBonusSpend`: gift before check; FIFO within category; partial lot consumption.
- Expiry job: предупреждения 7/3/1 день; сгорание; порог `expireNotifyMinBonuses`; флаги `warned*`.
- Coupon: reject redeem after expiry.
- Migration fixture: user с mixed ledger → корректные лоты.
- Admin: сохранение TTL, couponClaimDays, expireNotifyMinBonuses.

## Вне объёма

- Настраиваемые интервалы предупреждений (только 7 / 3 / 1 день).
- Предупреждения о сроке купонов (только бонусы).
- Разный TTL по местам розыгрыша.
- Пересчёт `expiresAt` при смене настроек админом.
- Отдельная админ-панель.
